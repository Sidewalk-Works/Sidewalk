# Operations runbook

Everything here refers to tools that exist in the repository and were run. Commands are from the repo root.

## Monitoring

`pnpm ops:check [--storage] [--strict] [--json]` is the one health command (cron or a systemd timer). Exit 0 healthy, 1 failed (`--strict`: warnings fail too). It checks the database and its time zone, applied migrations, the email outbox (stalled worker, dead messages, messages held for a missing key), the rate-limit store, and whether an administrator can use the admin tools. It reads counts only.

- `GET /api/v1/health` is liveness (no dependencies). `GET /api/v1/health/ready` checks database and storage and returns 503 when either is down.
- `/admin/email` shows the same outbox health to administrators, with banners for a stalled worker, held messages and a degraded rate-limit store.
- Logs are structured JSON with a request id (`x-request-id`, generated by the web gateway and echoed by the API). Alert on repeated `api_unreachable` lines from the web server and on `Rate-limit store unavailable` from the API.

## Upgrading an existing deployment

The migrations add tables and columns only. Existing addresses are **not** marked confirmed, because nobody has proved control of them; residents keep reading and signing in, and sessions stay valid.

1. Configure SMTP and `OUTBOX_ENCRYPTION_KEYS` (`pnpm outbox:keys generate`). Take a backup (below).
2. `pnpm account:upgrade preflight --check-smtp` (read-only, runs on the old schema). It lists who will be affected and blocks on a failing SMTP connection.
3. `pnpm db:migrate`, then restart API and worker.
4. `pnpm account:upgrade verify`. It fails while no administrator is confirmed.
5. Staff confirm through the emailed link, or, if you know them out of band: `pnpm account:upgrade confirm-email --staff --reason "..."` (dry run), then add `--apply`. Each change is audited with your reason. `admin:promote --confirm-email` does the same for the first administrator.

Rollback: restore the pre-upgrade backup. Do not drop the new tables by hand. Before rolling application code back, stop workers: older code cannot read the new ciphertext format and would mark queued messages dead.

## Outbox encryption keys

`OUTBOX_ENCRYPTION_KEYS` is `id:base64key,...`; the first key encrypts, the rest only decrypt. It is independent of `JWT_ACCESS_SECRET`.

- **Rotate:** `pnpm outbox:keys generate`, prepend the entry, restart API and worker, run `pnpm outbox:keys rewrap`.
- **Retire:** remove a key only when `pnpm outbox:keys status` shows no rows under it. A message whose key is missing is held (kept, no attempts used) and retried every 10 minutes; after a week it becomes dead with content retained, and an administrator can retry it once the key is back.
- **Legacy rows** (written before this change, encrypted with a JWT-derived key) stay readable while `OUTBOX_LEGACY_JWT_DECRYPT=true` and the JWT secret is unchanged. If that secret was already rotated, those rows cannot be recovered; they are held, then dead. Run `rewrap`, then set the flag to false.
- **Back up the keys** in a secret manager, separately from database backups.

## Rate limiting

Counted in PostgreSQL (`RateLimitBucket`, unlogged, fixed windows, HMAC-hashed keys, expired rows purged every minute). Exact across processes. If the database is slow or failing, requests fall back to a bounded per-process counter and the state is logged and shown in `/admin/email`. IPv6 clients are limited per /64. Sign-in failures are counted per account-and-address and per address; a very high per-account total only paces attempts, so nobody can lock out another person. Limits reset after a database crash.

Measured on a laptop: about 3,400 requests/s with the limiter versus 4,600 without, on a trivial endpoint. Move to a shared in-memory store only if you outgrow one database host.

## Backup and restore

```bash
pg_dump --format=custom --compress=6 --no-owner --no-acl "$DATABASE" > sidewalk.dump
pg_restore --no-owner --no-acl --exit-on-error -d "$SCRATCH_DATABASE" sidewalk.dump
```

`scripts/ops/backup-restore-check.sh [database]` does a real dump, restores it into `<database>_restore_check`, and compares every table by row count and content hash, plus indexes, constraints and the append-only triggers. Run it against a copy of production data on a schedule. Evidence objects need their own backup (bucket versioning or replication); `pnpm --filter @sidewalk/api storage:reconcile -- --check` reports missing and orphaned files.

## Drills

- `pnpm ops:drill`: kills a worker mid-send, simulates a mail outage, and shows recovery with each message delivered exactly once.
- `pnpm ops:prodlike`: two API processes plus a worker in `NODE_ENV=production` against a scratch database and a TLS mail sink.

## Incident checklist

1. `pnpm ops:check`; read `/admin/email`. 2. Mail not flowing: is the worker running, is SMTP reachable, are messages held for a key? 3. Suspected credential leak: rotate the secret (JWT rotation signs everyone out), then keys as above. 4. Bad deploy: stop workers, restore the backup, redeploy the previous build. 5. Record what happened; the audit log holds admin actions.

## Deployment prerequisites

Set `NEXT_PUBLIC_SITE_URL` (https) **at build time**: HSTS depends on it. Run the database in UTC (`ops:check` warns otherwise). Provide SPF, DKIM and DMARC for the sender domain (docs/security.md).
